# Issue #8 — Gateway Board Support

## Objective
Replace the failed ESP32-C6-LCD-1.47 target with the selected ESP32-S3-WROOM-1-N16R8 development-board candidate and an external 1.9-inch SPI ST7789 display, then validate the board profile, ESP-IDF build, resource/partition budget, and smoke tests.

## Problem and rationale
The original ESP32-C6-LCD-1.47 board is reported by the user as non-functional. The user selected an ESP32-S3-WROOM-1-N16R8 board (AliExpress item 1005006418608267) plus a separate 1.9-inch HD IPS SPI ST7789 display. No firmware exists yet, so the pivot is still low-cost. The board listing and a third-party YD-ESP32-S3 manual indicate a 44-pin dual-USB-C carrier, but the exact physical board revision and display module still need confirmation.

## Scope
- Replace the C6 target with the selected S3-WROOM-1-N16R8 development-board candidate in issue/project hardware documentation.
- Verify the physical carrier board, exposed pinout, two USB ports, RGB LED wiring, and external display model/pinout from reliable sources.
- Add the minimum ESP-IDF `esp32s3` gateway foundation only after the exact candidate setup supports strict TDD.
- Calculate flash, RAM, and display-buffer budgets; define a viable 16 MB partition table without silently removing gateway requirements.
- Define and run smoke checks for boot, onboard RGB, external LCD, and any other agreed peripheral.

## Out of scope
- Full gateway features, LVGL UI design, Sparkplug B, OTA implementation, and sensor-node migration.
- Assuming the external panel's resolution, pinout, voltage, or RGB order from “1.9-inch ST7789” alone.
- Claiming physical board/display validation without the selected hardware in hand.
- Silently dropping standalone dashboard or OTA requirements to simplify partitioning.

### [~] ODD-3 — Budget memory/flash and select a viable partition layout
**Status:** in progress on `feat/issue-8-s3-resource-budget`, based on the merged `main` containing PR #17. The parent must still perform final verification, create the ODD-3 work-unit commit, and record its identity before this task can be completed.
**Build and partition evidence:** ESP-IDF v5.4 custom partition mode generated and selected `partitions.csv`; the `partition-table` action and normal gateway build both passed. `gateway.bin` is 212,640 bytes (0x33EA0), leaving 2,933,088 bytes free (93%) in each 3 MiB OTA slot. Bootloader size is 21,008 bytes within 32 KiB. Static DIRAM is 57,499/341,760 bytes used, leaving 284,261 bytes. The reported IRAM 16,383/16,384 is the allocatable linker window after the I-cache carve-out, not total internal RAM.
**Validated layout:** two 3 MiB OTA app slots plus a 4 MiB SPIFFS partition, with standard NVS/OTA metadata/PHY partitions. This preserves the documented 2 MiB gateway-image ceiling and reserves room for a ≤500 KiB SPA plus a future ≤1.5 MiB node image staged by gateway OTA; future bundle/staging sizes remain targets, not measured artifacts. Candidate use ends at `0xA20000`. The alignment gap from the end of `phy_init` at `0x12000` to `ota_0` at `0x20000` is `0xE000` (56 KiB); the trailing unallocated range is `0xA20000` to `0x1000000`, `0x5E0000` (5.875 MiB). Together, the unassigned ranges total `0x5EE000` (5.9296875 MiB). Bootloader and partition-table bytes occupy their own flash outside app/data partitions and are not unallocated.
**Runtime evidence:** The separate Unity project built. The first monitor observed ROM `DOWNLOAD(USB/UART0)` while BOOT/GPIO0 was asserted. The user then released BOOT/GPIO0 and physically reset the board; the subsequent monitor of the already-flashed Unity app reported `2 Tests 0 Failures 0 Ignored` and `OK`. Before allocation, the minimal Unity test app reported 386,295 bytes free internal heap, 8,386,148 bytes free PSRAM, and an 8,257,536-byte largest PSRAM block. Allocation of one 108,800-byte (170 × 320 RGB565) 8-bit PSRAM block passed. These are measurements from the minimal test app, not the eventual full gateway firmware; they validate PSRAM allocation, not display DMA or throughput. The 45-second monitor ended with timeout exit 124 only after successful test output.
**Flash-layout boundary:** The hardware custom gateway partition table was build/parser-validated but not flashed. The device used the separate Unity app's default test layout. The Unity flash wrote bootloader, partition table, and app only to ESP-IDF-reported ranges `0x00000000–0x00005fff`, `0x00008000–0x00008fff`, and `0x00010000–0x00044fff`; no whole-chip erase occurred.
